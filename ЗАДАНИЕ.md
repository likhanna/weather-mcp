# Общая домашняя работа на выходные

## Weather MCP 2.0

Это итоговая работа по первым четырём урокам курса:

- основы работы с AI-агентом;
- инструменты Codex и MCP;
- структурированный промптинг;
- оркестрация и субагенты.

Задача продолжает практику пятого урока. Нужно реализовать новый MCP-инструмент `find_safe_weather_window` в проекте `weather-mcp`.

Срок: к началу следующего занятия.

Ориентировочное время: 3–5 часов.

## Рабочая копия

Создайте личную копию проекта или отдельную Git-ветку. Если Codex предлагает worktree, его также можно использовать.

## Требования к инструменту

Вход:

```json
{
  "city": "Dubai, United Arab Emirates",
  "work_type": "maintenance",
  "search_start": "2026-09-28T08:00",
  "search_end": "2026-09-28T18:00",
  "duration_hours": 3
}
```

Правила:

- время задаётся по Москве;
- `duration_hours` — целое число от 1 до 8;
- кандидаты начинаются каждый полный час;
- окно полностью помещается в заданный интервал;
- весь интервал находится в будущем и в пределах пяти суток;
- порядок риска: `LOW`, `MEDIUM`, `HIGH`;
- при равном риске побеждает меньшее количество факторов;
- при полном равенстве побеждает более раннее окно;
- результат содержит выбранное окно и до трёх альтернатив;
- число проверенных кандидатов возвращается в `structuredContent`;
- город, источник и время получения данных также возвращаются в `structuredContent`;
- неоднозначный и неизвестный город не выбирается автоматически;
- сбой Open-Meteo возвращает контролируемую ошибку без частичного результата;
- прогноз для всего интервала загружается одним внешним запросом;
- существующие инструменты `get_weather`, `assess_weather_risk` и `compare_weather_windows` сохраняют прежнее поведение.

## Обязательный процесс

### 1. Подготовить главный промпт

Создайте:

`prompts/homework-weather-mcp.md`

Промпт должен содержать цель, ограничения, критерии приёмки, требуемые артефакты, команды проверки и запрет на изменение существующих контрактов.

### 2. Использовать роли

Можно запустить субагентов либо выполнить роли в отдельных чатах:

- Analyst исследует текущую архитектуру.
- Planner создаёт Implementation Plan.
- Critic ищет логические ошибки и контрпримеры.
- Builder реализует одобренный план.
- Tester добавляет и запускает проверки.
- Reviewer проводит финальный review diff.

Не нужно держать всех агентов активными одновременно. Анализ и критика могут идти параллельно, реализация начинается после утверждения плана.

### 3. Хранить артефакты по одной задаче

Создайте папку:

`artifacts/HW-WEATHER-<фамилия>/`

В ней должны находиться:

- `task-spec.md`;
- `repo-map.md`;
- `implementation-plan-v1.md`;
- `plan-review.md`;
- `implementation-plan-v2.md`;
- `test-matrix.md`;
- `verification.md`;
- `final-review.md`.

Каждый файл начинается с идентификатора задачи `HW-WEATHER-<фамилия>`.

### 4. Реализовать инструмент

Разрешено менять только файлы, необходимые для функции, тестов и документации.

Ожидается:

- ясное разделение получения прогноза, построения кандидатов и ранжирования;
- отсутствие копирования порогов риска в несколько мест;
- Zod-схема входа;
- стабильный `structuredContent`;
- понятные MCP-ошибки;
- обновлённый README.

### 5. Проверить результат

Минимальная команда:

```powershell
npm run ci
```

Также вручную проверьте новый инструмент через MCP Inspector или подключённый Codex.

В `verification.md` сохраните:

- выполненные команды;
- результат сборки;
- количество прошедших тестов;
- два примера вызова нового tool;
- один успешный результат;
- один контролируемый отказ;
- известные ограничения.

Не вставляйте в отчёт секреты и токены.

2. Папку `artifacts/HW-WEATHER-<фамилия>/`.

4. Краткую рефлексию на 5–10 предложений:
