# Карта репозитория

Задача: `HW-WEATHER-Khannanova`

## Точки входа

- `weather-mcp/src/index.ts` создаёт `McpServer`, регистрирует инструменты через `server.registerTool(...)` и содержит исполняемую точку входа `main()` для STDIO.
- `weather-mcp/package.json` задаёт npm-команды; README описывает запуск через `npm run dev` / `npm start` и MCP Inspector.

## Модули и ответственность

- `weather-mcp/src/index.ts`: Zod-схемы аргументов, обработчики `get_weather`, `assess_weather_risk`, `compare_weather_windows`; форматирует `content`, `structuredContent` и `isError`.
- `weather-mcp/src/open-meteo.ts`: геокодирование, выбор единственного соответствующего города, запрос почасового прогноза, валидация ответа Open-Meteo, кэш успешной оценки и преобразование данных в типизированный результат.
- `weather-mcp/src/risk.ts`: единая реализация порогов температуры, осадков и ветра и агрегация по часам.
- `weather-mcp/src/time.ts`: строгий разбор `YYYY-MM-DDTHH:mm` как московского времени, перевод в UTC, ограничения будущего пятидневного горизонта и проверка пересечения часа с периодом.
- `weather-mcp/src/cache.ts`: нормализация/очистка названия города и память-кэш с TTL.
- `weather-mcp/src/health.ts`: необязательный локальный HTTP health endpoint; не относится к погодному расчёту.

## Поток данных текущей задачи

1. MCP принимает аргументы; схема и обработчик нового инструмента должны быть зарегистрированы в `weather-mcp/src/index.ts` (так же сделаны три существующих инструмента).
2. `weather-mcp/src/time.ts::parseWorkPeriod` преобразует московские wall-clock дату и длительность в UTC и отвергает прошлое/горизонт более пяти суток. Сейчас функция принимает один старт и положительную дробную длительность; требуемые целочисленные 1–8 и интервальная генерация кандидатов отсутствуют.
3. `weather-mcp/src/open-meteo.ts::OpenMeteoRiskService.assess` сначала геокодирует, затем делает отдельный forecast fetch, проверяет все затронутые часы и вызывает `assessRisk`. Таким образом, повторный вызов `assess` для каждого кандидата вызовет несколько погодных запросов (если разные ключи кэша), что не соответствует требованию одного forecast-запроса на весь поиск.
4. `weather-mcp/src/risk.ts::assessRisk` добавляет фактор по каждому часовому значению и метрике, выбирает максимальный уровень (`HIGH` > `MEDIUM` > `LOW`); `factors.length` поэтому доступен как количество факторов для оценки периода.
5. `weather-mcp/src/index.ts::compare_weather_windows` показывает действующий стиль: валидация обоих периодов до оценки, единый сервис, controlled `isError`, structured result. Он сравнивает только уровни риска; факторы и более раннее время не участвуют.

## Публичные контракты

- Имена и входы существующих tools: `get_weather(city, days)`, `assess_weather_risk(city, start_at, work_type, duration_hours)`, `compare_weather_windows(city, work_type, windows[2])` описаны в `weather-mcp/src/index.ts` и `weather-mcp/README.md`; домашнее задание запрещает изменение их поведения.
- Текущий `assess_weather_risk` возвращает результат assessment в `structuredContent`; `not_found` и `ambiguous` возвращаются как controlled MCP errors с объектом результата; ошибки исключений возвращают `isError` без структурированного частичного результата.
- Новое имя `find_safe_weather_window` и его поля должны быть самостоятельным MCP-контрактом; требуемая форма результата подробно в исходнике не определена, кроме выбранного окна, до трёх альтернатив и метаданных.

## Гипотезы и пробелы

- Подтверждён факт: риск периода агрегируется максимумом риска отдельных затронутых часов (`weather-mcp/src/risk.ts`). Не определено, будет ли для окна кандидата применён тот же максимум или другая агрегация.
- Подтверждён факт: факторы сейчас являются отдельными событиями (час + метрика), а не уникальными типами метрик (`weather-mcp/src/risk.ts`). Не определено, считать ли в критерии tie-breaker именно длину `factors` или уникальные факторы.
- Формат существующих временных строк — `YYYY-MM-DDTHH:mm`, без смещения, московское время; включительность `search_end` и поведение при минутных границах нового диапазона условием не уточнены.
- Существующий forecast парсер требует данные для каждого часа пересечения периода (`weather-mcp/src/open-meteo.ts`); требуемый горизонт нового одного запроса и включённость последнего часового bucket должны быть отдельно спроектированы.
