## Прямые зависимости задачи

- `@modelcontextprotocol/server` — runtime MCP server (`^2.0.0`; зафиксирован `2.0.0`). Исходный `src/index.ts` импортирует `McpServer` и STDIO transport; новый инструмент должен использовать существующий server API.
- `zod` — runtime валидация схемы (`^4.0.0`; зафиксирован `4.6.5`), импортируется как `zod/v4` в `src/index.ts`. Для `duration_hours` и временных полей задача требует Zod-схему; дополнительный пакет по имеющимся требованиям не нужен.
- Новые прямые зависимости не указаны и по доступным манифестам не требуются. MCP client и Inspector относятся к локальной проверке/разработке, а не к runtime сервера.

Источник версий и назначений: [package.json](../../weather-mcp/package.json), [package-lock.json](../../weather-mcp/package-lock.json), [src/index.ts](../../weather-mcp/src/index.ts).

## Транзитивные зависимости

- Lockfile v3 фиксирует полное дерево пакетов. `@modelcontextprotocol/server@2.0.0` зависит от `@modelcontextprotocol/core@2.0.0` и `zod ^4.2.0`; верхнеуровневый lock содержит совместимый `zod@4.6.5`.
- Dev dependency `@modelcontextprotocol/client@2.0.0` также зависит от MCP core и включает transport/auth пакеты (`cross-spawn`, `eventsource`, `eventsource-parser`, `jose`, `pkce-challenge`) и Zod. `@modelcontextprotocol/inspector@2.7.0` подтягивает client/server и веб-интерфейсные зависимости, включая Hono/Vite/React и др. Это крупное дерево используется Inspector, но не попадает в Docker runtime: второй stage выполняет `npm ci --omit=dev`.
- `tsx@4.23.15` зависит от `esbuild ~0.28.0`; TypeScript-компилятор и Node typings также dev-only. Полный набор точных версий, integrity и resolved URL записан в lockfile. Источники: [package-lock.json](../../weather-mcp/package-lock.json), [Dockerfile](../../weather-mcp/Dockerfile).
- Лицензии в lockfile можно проверить для отдельных пакетов (например, MCP server/core/client и Zod отмечены MIT, TypeScript — Apache-2.0). Сводный аудит лицензий всего дерева для этой задачи не найден и не выполнялся.

## Внешние сервисы и данные

- Источник геокодирования: `https://geocoding-api.open-meteo.com/v1/search`; источник прогноза: `https://api.open-meteo.com/v1/forecast`. API-ключ в README не требуется. В коде `OpenMeteoRiskService` геокодирует город, не выбирает неоднозначное совпадение автоматически, затем запрашивает почасовые `temperature_2m`, `precipitation_probability` и `wind_speed_10m` с единицами ветра `ms`, `timezone=UTC` и `forecast_days=6`. Источник: [src/open-meteo.ts](../../weather-mcp/src/open-meteo.ts); также endpoints видны в [src/index.ts](../../weather-mcp/src/index.ts).
- Для целевой задачи ожидаются отдельный геокодинговый вызов и один внешний forecast-вызов на поисковый интервал (если результат не взят из кэша); прогноз затем локально используется для оценки всех кандидатов. Это согласуется с текущим шаблоном «геокодирование → forecast», но объединённый поиск нескольких окон в текущем API отсутствует — реализация должна явно подтвердить ровно один forecast fetch для нового вызова.
- Запросы сделаны встроенным `fetch`, с `AbortSignal.timeout(5_000)`; сетевые/HTTP/JSON ошибки переводятся в контролируемую ошибку погоды. Результаты оценки кэшируются в памяти процесса на 10 минут. README указывает, что пользовательские запросы и координаты не записываются на диск. Источники: [src/open-meteo.ts](../../weather-mcp/src/open-meteo.ts), [src/cache.ts](../../weather-mcp/src/cache.ts), [README.md](../../weather-mcp/README.md).
- Внешняя доступность и формат ответа Open-Meteo — операционная зависимость без локального fallback; она должна оставаться полностью отказоустойчивой для нового инструмента: при сбое единственного forecast-запроса не возвращать частичный список вариантов, согласно task-spec.

## Совместимость версий

- `package.json` задаёт caret ranges (`@modelcontextprotocol/server ^2.0.0`, `zod ^4.0.0`, dev-пакеты также ranges), а `package-lock.json` фиксирует фактические версии и `npm ci` в обоих Docker stages устанавливает их детерминированно. Для воспроизводимой проверки следует использовать `npm ci`, а не обновлять lock произвольно.
- `@modelcontextprotocol/inspector@2.7.0` объявляет Node `>=22.19.0`, тогда как пакет в целом допускает Node `>=20`. Поэтому требование Node 20 относится к сборке/запуску сервера в целом, но скрипт Inspector может не запускаться на Node 20; образ проекта Node 24 удовлетворяет этому ограничению. Источники: корневой блок lockfile для Inspector, [package.json](../../weather-mcp/package.json), [Dockerfile](../../weather-mcp/Dockerfile).
- Новая логика должна переиспользовать существующий `assessRisk` и модели `HourlyWeather`, чтобы не расходились пороги/типизация; этот модуль не добавляет пакетных зависимостей. Источник: [src/risk.ts](../../weather-mcp/src/risk.ts).
- Окно поиска задачи ограничено пятью будущими сутками, а существующий сервис запрашивает шесть дней прогноза. Это, вероятно, покрывает горизонт, но включительность граничного часа, соответствие московских локальных времён UTC-часам прогноза и наличие всех часовых значений на конце диапазона нужно проверить отдельно; по одному только манифесту совместимость временных границ не гарантируется.

## Риски и требуемые проверки

- После согласования реализации выполнить `npm run ci` (скрипт запускает TypeScript build и Node tests), включая тест, подтверждающий один forecast-запрос на интервал и отказ без частичного результата. На текущем этапе команды не запускались.
- Отдельно вручную проверить успешный и отказной MCP-вызовы через Inspector или Codex — это acceptance criterion в `task-spec.json`. Учесть версию Node Inspector `>=22.19.0`; README использует Node 20+ для проекта в целом.
- Проверить регрессию трёх существующих tools и неизменность их контрактов; новое вычисление должно вызывать общую risk-логику, не вносить новые пороги.
- Нужны проверки API timeout/HTTP/ошибочного JSON, неоднозначной локации, нехватки данных на краях диапазона и единичного forecast failure. Ошибки и отсутствие данных не должны возвращать частичный результат.
- README упоминает Open-Meteo API как бесплатный и без ключа, но файлы проекта не подтверждают SLA, квоты/ограничения конкретных endpoint-ов, лицензию условий использования данных или гарантированный горизонт/частоту обновления прогноза. При необходимости эти внешние условия следует сверить с актуальной документацией перед выпуском.
- Удалённой CI-конфигурации и подтверждённого Docker build в материалах проекта нет; без запуска проверки нельзя утверждать, что локальный CI или образ проходит.

## Гипотезы и пробелы

- Набор входов задачи говорит об одном прогнозе на интервал, но существующий кэш `OpenMeteoRiskService` адресует результаты по городу, конкретному старту, типу работы и длительности. Новый агрегирующий tool, вероятно, должен выполнять собственный flow или переиспользовать низкоуровневые функции, не вызывая оценку по каждому кандидату (иначе получится несколько forecast fetch-ов). Точная архитектура здесь не предписывается.
- `task-spec.json` фиксирует московское время без смещения; README документирует тот же формат для текущего инструмента. Следует согласовать временную нормализацию/границы кандидатов в плане: зависимость от дополнительных timezone-библиотек по текущим файлам не подтверждена; `Intl`/встроенные API Node могут быть достаточны, но это требует проверки реализации.
- Не обнаружены отдельные сведения об уязвимостях, полном составе лицензий, расписании обновлений или гарантиях доступности; выводы о них не делались.
- Локальные `node_modules` присутствуют в рабочем дереве, однако состояние этих установленных файлов не использовалось как lock-источник; зафиксированные версии указаны по `package-lock.json`.
