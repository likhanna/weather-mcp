HW-WEATHER-Khannanova

# Спецификация задачи

Идентификатор: `HW-WEATHER-Khannanova`

## Цель

Добавить в `weather-mcp` MCP-инструмент `find_safe_weather_window`, который находит и ранжирует будущие почасовые окна для указанного типа работ на основе одного загруженного прогноза Open-Meteo. Существующие MCP-инструменты должны сохранить контракты и поведение.

## Подтверждённые требования

- Вход: `city`, `work_type`, `search_start`, `search_end`, `duration_hours`.
- Время ввода — московское, пример формата согласуется с существующими `YYYY-MM-DDTHH:mm`.
- `duration_hours` — целое число от 1 до 8 включительно.
- Кандидатные старты идут каждый полный час; каждое окно целиком находится в поисковом интервале.
- Весь поисковый интервал будущий и ограничен пятью сутками.
- Порядок уровней риска: `LOW < MEDIUM < HIGH`; при одинаковом уровне выигрывает меньшее количество факторов, затем более ранний кандидат.
- Возвращаются победитель, максимум три альтернативы и число проверенных кандидатов в `structuredContent`.
- `structuredContent` содержит город, источник и время получения данных.
- Неоднозначное и неизвестное геокодирование не выбирает локацию автоматически.
- Сбой Open-Meteo приводит к контролируемой ошибке без частичного результата.
- Forecast на интервал поиска получают одним внешним прогнозным запросом.
- Не меняются поведение и контракты `get_weather`, `assess_weather_risk`, `compare_weather_windows`.
- Ожидаются Zod-схема, понятные MCP-ошибки, стабильный `structuredContent`, отсутствие копирования порогов риска, обновление README.
- Проверки после реализации: `npm run ci`, успешный и отказной вызовы через MCP Inspector или Codex; отчёт фиксирует команды, результаты и ограничения.
- Дополнительный критерий: генеративная/property-based проверка корректности ранжирования, границ окна и инвариантности перестановки кандидатов.

## Архитектурные факты

- `weather-mcp/src/time.ts` разбирает московское локальное время формата `YYYY-MM-DDTHH:mm` и проверяет горизонт на основе одного периода.
- `weather-mcp/src/risk.ts` реализует общие погодные пороги и агрегирует риск периода по максимальному уровню среди часов; факторы сейчас считаются как события по часу и метрике.
- `weather-mcp/src/open-meteo.ts` выполняет геокодирование и один forecast запрос для одной оценки, требует полноту затронутых часовых данных.
- `weather-mcp/src/index.ts` регистрирует инструменты и формирует MCP `structuredContent`/ошибки.
- Эти факты не разрешают сами по себе бизнес-неопределённости, перечисленные ниже.

## Критерии приёмки

1. MCP tool зарегистрирован под точным именем `find_safe_weather_window`; Zod-валидация принимает только длительность целым 1–8.
2. Некорректный, прошлый или выходящий за горизонт поиска отклоняется до внешних запросов.
3. Создаются только старты по полным часам; окна полностью помещаются в интервал поиска.
4. Геокодирование сохраняет существующее поведение: unknown/ambiguous не выбираются автоматически.
5. Для прогноза на весь диапазон выполняется ровно один погодный запрос; недостаточный/битый ответ и сбой дают controlled error без частичного списка.
6. Расчёт использует существующие пороги без дублирования; детерминированный порядок: уровень риска, число факторов, более раннее окно.
7. Результат стабильно содержит выбранное окно, до трёх альтернатив, число проверенных кандидатов, город, source и fetched_at в `structuredContent`.
8. Регрессионные проверки подтверждают неизменность поведения трёх прежних инструментов.
9. Обновлён README; `npm run ci` и два ручных MCP вызова имеют записанные результаты в verification артефакте.
