# Вопросы по задаче

Идентификатор: `HW-WEATHER-Khannanova`

## Обсуждавшиеся блокирующие решения

1. **Как агрегировать риск по часам внутри одного кандидатного окна?** Текущий `assessRisk` в `weather-mcp/src/risk.ts` выбирает наивысший уровень за период; подтвердите, что новый инструмент применяет то же правило к каждому кандидату. Иначе разные допустимые варианты агрегации могут выбрать разные окна.
2. **Что означает «количество факторов» при tie-break?** `assessRisk` создаёт фактор на каждую комбинацию часа и метрики; считать все события `factors.length` или уникальные метрики/типы факторов на всё окно? Это непосредственно меняет порядок окон с одинаковым уровнем риска.
3. **Как трактовать правую границу `search_end`?** Включительна ли она как допустимый конец работы, при условии `candidate_start + duration <= search_end`, и должен ли `search_end` быть кратен полному часу? Это определяет наличие кандидата на границе и случаи без кандидатов.
4. **Какие минуты допустимы во входных `search_start` и `search_end`?** Пример использует `08:00`/`18:00`, существующий формат разрешает любые минуты, тогда как кандидаты должны начинаться по полным часам. Нужно подтвердить разрешение минутного диапазона и правило округления к первому часовому старту не раньше `search_start`.
5. **Проверка будущего/пяти суток относится к границам search interval или ко всем возвращаемым кандидатам?** Формулировка требует, чтобы весь интервал находился в будущем и в пределах пяти суток, но точная точка отсчёта (текущий момент либо `now + 5d`) не названа явно. Существующая `parseWorkPeriod` проверяет старт не раньше now и окончание не позже now+5d.

## Неблокирующие уточнения

1. **Форма объекта выбранного окна и альтернатив.** Условие задаёт их содержимое на уровне понятий, но не поля. Ответ позволит зафиксировать стабильную схему нового `structuredContent`, не затрагивая старые контракты.
2. **Должно ли поле `city` в метаданных означать нормализованное отображаемое имя Open-Meteo или исходную пользовательскую строку?** Это влияет только на точный смысл метаданных результата.
3. **Нужен ли `work_type` в каждой записи окна, или только на верхнем уровне?** Тип одинаков для всех кандидатов, поэтому этот выбор не меняет ранжирование.

## Принятые решения

Пользователь одобрил `implementation-plan-v2.md` 2026-09-27 до реализации. Приняты: полуоткрытый поиск с разрешённым `candidate_end == search_end`; `search_start >= now` и `search_end <= now + 5 суток` в одном snapshot; округление первого старта вверх; оценка через существующий `assessRisk`; tie-break по `factors.length`, затем ранний старт; один forecast запрос после отдельного geocoding; без кэша для нового flow; controlled error без partial structuredContent, если кандидатов нет; публичные поля ответа — как в v2. Неотвеченных вопросов для одобренной реализации нет.

## Зафиксированные наблюдения

- Дата принимается существующей логикой как точный формат `YYYY-MM-DDTHH:mm` в московском времени; см. `weather-mcp/src/time.ts` и `weather-mcp/README.md`.
- Час прогноза считается затронутым при пересечении полуоткрытых интервалов; см. `intersectsHour` в `weather-mcp/src/time.ts`.
- Риск периода — максимум по часам, а список факторов сохраняет каждый час/метрику; см. `assessRisk` в `weather-mcp/src/risk.ts`.
- Ни `ЗАДАНИЕ.md`, ни README не определяют правила списка факторов при сравнении кандидатных окон.
