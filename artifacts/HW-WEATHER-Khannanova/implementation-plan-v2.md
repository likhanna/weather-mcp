**Статус:** одобрен пользователем 2026-09-27; разрешение распространяется только на область ниже. Сборка, тесты и ручные MCP-вызовы не запускались до реализации.

## Цель и границы

Добавить только новый MCP-инструмент `find_safe_weather_window`, необходимые внутренние функции и типы, тесты и описание в README. Существующие `get_weather`, `assess_weather_risk`, `compare_weather_windows` сохраняют имена, схемы аргументов, результаты и поведение. Новых зависимостей не добавлять. Внешних изменений/релиза нет.

## Предлагаемое решение

1. В `weather-mcp/src/time.ts` добавить независимый разбор поискового интервала и генератор канонических кандидатов; не менять `parseWorkPeriod` или `intersectsHour`.
2. В `weather-mcp/src/open-meteo.ts` добавить отдельный метод поиска. Он проверяет вход с одним snapshot `now`, генерирует кандидатов, выполняет текущее геокодирование с отказом для `not_found`/`ambiguous`, делает один forecast-запрос и рассчитывает все окна локально через существующий `assessRisk` из `risk.ts`. Новый flow не вызывает `assess()` на каждый кандидат и не использует cache: каждое успешное выполнение получает один свежий прогноз, а `fetched_at` означает фактическое время получения этого forecast-ответа.
3. В `weather-mcp/src/index.ts` зарегистрировать новый Zod tool с `.strict()` и отдельным обработчиком контролируемых ошибок. Остальные handlers не рефакторить.
4. Вынести чистое сравнение/сортировку в отдельную функцию (в `time.ts` или `weather-windows.ts`); пороги погодного риска остаются только в `risk.ts`.

## Предлагаемые точные семантики для одобрения

Эти пункты являются проектными решениями, а не утверждением, что текст задания их уже задаёт.

- Времена — существующий формат `YYYY-MM-DDTHH:mm`, Московское время (`UTC+03:00`). Разбор перевести в UTC до сравнения и округления; минутные значения на `search_start`/`search_end` допустимы.
- Поиск трактуется как полуоткрытый интервал `[search_start, search_end)`, но рабочее окно разрешено, если его конец равен `search_end`: `start >= search_start && end <= search_end`.
- Валидность проверяется одним значением `now`: `search_start >= now`, `search_end > search_start`, `search_end <= now + 5 суток`. Таким образом, точное равенство границе допускается, на одну минуту позже — нет.
- Первый кандидат — первый полный московский час `>= search_start`; последующие старты идут с шагом ровно один час. Канонический генератор создаёт не более одного кандидата на start.
- Для длительности N часов оцениваются прогнозные записи для каждого из N полных UTC-часов `[candidate_start, candidate_end)`. Внутреннее агрегирование — существующий `assessRisk` (максимальный уровень по часам); tie-break количество факторов — `factors.length` (события «час × метрика», максимум `3 × duration_hours`), затем более ранний `start_at`.
- Ранжируются только уникальные кандидаты канонического генератора. Полностью одинаковый кандидат не может возникнуть дважды; генеративная проверка перестановки использует множество уникальных стартов. Comparator сортирует tuple `(risk_rank, factors.length, start_utc)`.
- Число `candidates_checked` — число всех допустимых временных окон, оценённых перед усечением альтернатив. Успех возвращает лучший и следующие максимум три окна.
- Если валидный интервал не содержит ни одного целого помещающегося окна, вернуть controlled MCP error `isError: true` без `structuredContent` (рекомендованный текст: «В заданном интервале нет подходящих почасовых окон для указанной длительности.»). Успешный ответ с пустым победителем не используется.
- Геокодирование является отдельным запросом и не входит в ограничение одного запроса прогноза. Для одного вызова: максимум один geocoding request по текущему flow и ровно один forecast request после единственной однозначной локации. Неоднозначность/отсутствие города завершает обработку до прогноза.
- Forecast запрашивает существующие переменные `temperature_2m,precipitation_probability,wind_speed_10m`, `wind_speed_unit=ms`, `timezone=UTC`, `forecast_days=6`. Из ответа валидируется объединение часов, реально требуемых всеми допустимыми кандидатами, а не час, который только пересекает исходный интервал поиска. Для каждого кандидата должны быть все его N последовательных buckets. Отсутствие любого нужного bucket — единая controlled ошибка без победителя или альтернатив. На максимальном горизонте отдельно проверить, что последний нужный bucket попадает в ответ Open-Meteo.
- Кэширование для нового tool не вводится; `fetched_at` — UTC ISO timestamp получения успешного forecast response, а не время геокодирования, сортировки или кэширования.

## Предлагаемый публичный результат

При успехе `structuredContent` имеет стабильную форму:

```json
{
  "selected_window": {
    "start_at": "2026-09-28T09:00",
    "end_at": "2026-09-28T12:00",
    "duration_hours": 3,
    "risk_level": "LOW",
    "recommendation": "PROCEED",
    "factors": []
  },
  "alternatives": [],
  "candidates_checked": 7,
  "location": {
    "city": "Dubai",
    "country": "United Arab Emirates",
    "timezone": "Asia/Dubai"
  },
  "work_type": "maintenance",
  "source": "Open-Meteo",
  "fetched_at": "2026-09-27T12:00:00.000Z"
}
```

`alternatives` содержит до трёх объектов той же формы, что `selected_window`, в отсортированном порядке. `factors` сохраняет формат существующего `RiskFactor[]`. Поля с отсутствующим region опускаются. В `content` возвращается то же представление результата. Поля/названия являются новым публичным контрактом и входят в одобряемый план.

## План шагов и доказательств

1. **Интервал и кандидаты.** Валидировать формат/даты/порядок/горизонт до сети; получить кандидаты по полным часам и не выходить за обе границы. Unit-тесты для :00/:01/:30/:59, перехода даты, длительности 1/8, окончания точно на `search_end`, конца на минуту позже, пустого множества, `now`, `now+5d` и `now+5d+1min`.
2. **Полнота данных и оценка.** Получить часы по единственной однозначной локации одним forecast-запросом. Валидировать только объединение buckets всех кандидатов, для каждого окна требовать ровно N последовательных часов. Тест `10:30–13:00`, duration 2: кандидат 11:00–13:00 требует buckets 11 и 12, но не 10; дополнительно проверить последний нужный bucket около `now+5d`. Missing bucket/timeout/HTTP/JSON failure дают controlled отказ без частичного ответа.
3. **Ранжирование и контракт.** Применить `assessRisk`, сравнить `(LOW<MEDIUM<HIGH, factors.length, start_utc)`, вернуть победителя/до трёх альтернатив и метаданные. Проверить 4+ окон, полный tie-break, `factors.length <= 3*N`, счёт всех оценённых кандидатов и MCP schema/result/error.
4. **Property/generative тест.** Без новой библиотеки, встроенным `node:test` и фиксированным seed, проверить не менее 1000 диапазонов сравнением с независимым oracle: alignment, containment, duration, уникальность стартов, точный count, победитель не хуже альтернатив. Перестановка уникальных кандидатов не меняет ранжированный результат; дубликаты стартов не генерируются.
5. **Совместимость и документация.** Сохранить тесты существующих tools, проверить список MCP (добавлено ровно одно имя), обновить README. После пользовательского approval выполнить `npm run ci`, вручную проверить успешный и controlled-error вызовы через Inspector или Codex и только фактические результаты записать в `verification.md`/`final-review.md`.
