# Главный промпт: домашняя работа Weather MCP 2.0

## Задача

Реализуй новый MCP-инструмент `find_safe_weather_window` в проекте `weather-mcp`. Цель — найти самое безопасное окно для указанного типа работ в заданном диапазоне по московскому времени. Используй task key `HW-WEATHER-Khannanova` и артефакты из `artifacts/HW-WEATHER-Khannanova/`.

До начала реализации пользователь должен просмотреть и одобрить `implementation-plan-v2.md`. До этого разрешены только анализ, проектирование и правки артефактов планирования; исходный код, тесты и README не изменять.

## Вход инструмента

```json
{
  "city": "Dubai, United Arab Emirates",
  "work_type": "maintenance",
  "search_start": "2026-09-28T08:00",
  "search_end": "2026-09-28T18:00",
  "duration_hours": 3
}
```

Время интерпретируется по Москве. `duration_hours` — целое число от 1 до 8. Кандидаты начинаются каждый полный час, целиком помещаются в интервал поиска, а весь поисковый интервал находится в будущем и не далее пяти суток от текущего времени.

## Правила выбора

Оценивай риск каждого подходящего окна в соответствии с существующими порогами проекта, не копируя пороги в несколько мест. Упорядочивай результат по возрастанию риска (`LOW`, `MEDIUM`, `HIGH`), затем по меньшему количеству факторов риска, затем по более раннему началу. Результат содержит лучший вариант и не более трёх следующих вариантов.

Получай прогноз для всего интервала одним внешним запросом Open-Meteo. Неизвестный или неоднозначный город не выбирай автоматически. При сбое Open-Meteo возвращай контролируемую MCP-ошибку без частичного результата.

`structuredContent` должен стабильно содержать выбранное окно, альтернативы, число проверенных кандидатов, разрешённый город, источник данных и время получения данных. Финальные имена и типы полей фиксируй в одобренном плане.

## Ограничения и совместимость

- Существующие `get_weather`, `assess_weather_risk` и `compare_weather_windows` сохраняют прежнее поведение и публичные контракты MCP.
- Добавь входную Zod-схему и понятные ошибки в стиле проекта.
- Раздели получение прогноза, генерацию кандидатов и ранжирование.
- Не расширяй задачу без согласования; секреты и токены не включай в артефакты.
- Изменения разрешены только в файлах, необходимых для нового инструмента, его тестов и документации.

## Критерии приёмки

1. Валидация ограничивает длительность целыми значениями 1–8 и отклоняет некорректные/небудущие/слишком дальние интервалы.
2. Кандидаты стартуют только в полные часы, полностью помещаются в границы поиска и считаются корректно на границах.
3. Для интервала выполняется один запрос прогноза; при сетевой ошибке ответ не содержит частичных окон.
4. Все окна ранжируются детерминированно по уровню риска, числу факторов и времени начала.
5. Ответ включает лучший вариант, до трёх альтернатив и стабильные метаданные в `structuredContent`.
6. Неоднозначные/неизвестные города требуют уточнения; автоматического выбора нет.
7. Старые инструменты и их аргументы/результаты/ошибки не регрессируют.
8. README описывает новый инструмент. `npm run ci` проходит, а ручная проверка через MCP Inspector или Codex содержит успешный вызов и контролируемый отказ.
